# D1 Billable-Usage & Index-Remediation Rules

Rules for diagnosing D1 read-cost overages and safely adding indexes. This repo
uses **Drizzle ORM on Cloudflare D1** — there is **no Prisma**. Follow these
exactly; the source example this was adapted from mixed in Prisma/Durable-Object
concepts that do **not** apply here.

## The stack, stated plainly

- **One D1 database**, bound as `DB` (see `wrangler.jsonc` → `d1_databases`).
- **Schemas** live per-table under `src/backend/db/schemas/**` (barrelled by
  `src/backend/db/schema.ts`). Indexes are declared with Drizzle's `index()` in
  the table's own file — see `governance/usage-snapshots.ts` for the canonical
  pattern.
- **Migrations** are generated by `drizzle-kit` into `./drizzle` (see
  `drizzle.config.ts` → `out: "./drizzle"`) and applied with
  `wrangler d1 migrations apply DB`.
- **Aggregate cost/usage** is already tracked in-app: `guardian/billable-usage.ts`
  (real charged cost, Billable Usage API) and `guardian/daily-cost.ts`
  (reconstructed estimate). Those give **per-product** totals, not per-query
  hotspots — use `wrangler d1 insights` for that.

## Rules

- **Diagnose before editing.** Never guess index placement. Identify the hot
  table/query first:
  ```bash
  npx wrangler d1 insights DB --sort-by reads --sort-direction DESC
  ```
  The offenders are queries doing `SCAN TABLE` (no usable index for their
  `WHERE`/`ORDER BY`/join key).
- **Pre-flight backup is mandatory.** Any schema change to `DB` MUST be preceded
  by a Drive archive of the affected data, using the **existing** archive flow —
  `src/backend/lib/google-drive.ts` (resumable upload + byte-count audit) driven
  from the `ArchiveD1Dialog` / `DriveConfig` UI. Do **not** write a new backup
  script. The archive is only "confirmed" once the byte-count audit matches (the
  `action_items` audit row is the proof); do not proceed to a migration until
  then. Archive flows never auto-delete.
- **Indexes go in the Drizzle schema, not raw SQL.** Add the `index()`
  declaration to the table's file under `src/backend/db/schemas/**`, covering the
  foreign key or `WHERE`/`ORDER BY` target that caused the scan. Then generate the
  migration — never hand-write migration SQL:
  ```bash
  pnpm run db:generate         # drizzle-kit → new file under ./drizzle
  pnpm run migrate:remote      # db:generate + wrangler d1 migrations apply DB --remote
  ```
- **Migration path is `./drizzle`.** Automated migrations for D1 target `./drizzle`
  (the `drizzle-kit` output dir). There is **no** `prisma/migrations/{db_name}` in
  this repo — do not create one.
- **`new_sqlite_classes` does not apply here.** That key configures **Durable
  Object** SQLite migrations in `wrangler.jsonc` (`migrations` array); it has
  nothing to do with adding a D1/Drizzle index. Do not add index changes to the
  DO `migrations` block.
- **PR for review, never auto-apply to prod unattended.** Schema/migration changes
  open a Pull Request for manual review. `migrate:remote` runs as part of `deploy`
  after the PR merges — not from an ad-hoc agent run.

## Worked example (already done)

`usage_snapshots` is append-only and never pruned, so it was the account's
largest D1 rows-read driver. The fix was two `index()` declarations —
`idx_usage_snapshots_ts` and `idx_usage_snapshots_service_ts` — matching how every
reader filters (`timestamp`, or `service`+`timestamp`). See
`src/backend/db/schemas/governance/usage-snapshots.ts`. New offenders follow the
same shape: match the index to the query's filter/sort columns.
